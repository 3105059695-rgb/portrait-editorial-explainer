# 可迁移的 UI 设计系统

这份规则用于把不同题材做成同一类 UI 讲解：清楚的信息层级、有内容的界面、可辨认的操作反馈，以及服务阅读的运动。固定的是这些设计关系；布局、素材、状态顺序和剪辑方式由本期内容决定。

代码与时序字段见 [UI 组合契约](ui-composition-contract.md)。这里先决定画面应当是什么，再交给部件绘制。

## 1. 从话意选择信息结构

先写一句“观众需要理解什么”，再选择一种结构。下表只提供结构例子，不指定镜头模板。

| 信息关系 | 可以使用的界面结构 | 可见状态变化 |
|---|---|---|
| 从多项里找到一项 | 有具体内容的列表或网格、筛选区、详情区 | 条件变化、候选收敛、选中、详情更新 |
| 比较选择 | 对齐指标的两列或多行、当前选择、解释区 | 指标高亮、条件切换、差异显现 |
| 过程与结果 | 工作区、当前任务、结果区 | 参数改变、处理反馈、结果出现 |
| 修改或整理信息 | 编辑区、来源区、修改记录或结构视图 | 对象移动、字段改变、顺序调整 |
| 趋势与规模 | 有来源的数据图表、范围控制、解释标签 | 时间窗口变化、数据点出现、局部聚焦 |
| 解释抽象关系 | 带标签的对象图、关联线、状态标记 | 分组、连接、拆分、位置或状态改变 |

不涉及应用操作的概念可以使用最后一类，不必伪装成软件教程。真实软件演示优先使用允许使用的截图或素材；为讲解而设计的界面标“示意界面”，不能让观众误以为是产品实测。

## 2. 让界面有内容，而不是空壳

在设计稿中明确三个层级：

- **上下文**：名称、导航、当前任务、必要的列表或图像，让观众知道在哪里。
- **当前动作**：一项正在处理的内容及对应控制，视觉最突出。
- **反馈**：选中态、修改后的数值、展开内容、完成结果，操作前后看得出差别。

三个层级可以处于同一个窗口或对象图，不需要三个大面板。只保留有用控制；每个按钮、输入框、标签都应能解释其作用。内容应包含本期具体短文本、图像、条目、来源或有意义的数据，不以一整屏“示例文字”交差。

信息丰富不等于小字堆满。列表可先显示 3–6 个有区别的条目，详情保留最相关的 2–4 项字段；这是起点，按内容增减。重要内容用镜头和层级变得可读，次要上下文保持安静。图表采用可解释的数据；演示数字标明示意，不能编造真实结论。

## 3. 视觉规则与起始参数

以下数值是宽 544 逻辑画布上的设计起点，非原片测量值或每期固定值。最终以实际 360–430 像素宽的手机预览是否可读为准。

| 项目 | 起点 | 判断标准 |
|---|---|---|
| 画布 | 近白或浅暖灰；需要解释强调时使用浅色舞台 | 主体与背景有层次，颜色变化有语义 |
| 颜色 | 深灰正文、柔和灰线、一个主强调色；辅助状态色少量使用 | 一眼能找到当前动作，非所有部件同时鲜艳 |
| 外边距 | 约 24–36 | 主体不会贴边；竖屏字幕与人物另留空间 |
| 对齐和间距 | 常用间距 8、12、16、24，按内容调整 | 相同信息角色对齐，分组一眼可辨 |
| 标题 | 26–36；有编辑感的粗体，关键词适度强调 | 明确本段主题，不挤占全部界面 |
| 界面文字 | 当前操作 16–20；次要信息 13–16 | 镜头贴近时可读；小字不承担核心论点 |
| 边框与圆角 | 约 1–1.5 的细边；圆角 8–16 | 窗口、按钮和标签各有形态，不全变圆卡片 |
| 层次 | 轻接触阴影；浮层可略强，背景区更平 | 能辨认页面、浮层、当前对象三者关系 |
| 漫画强调 | 约 3–4 的深轮廓、硬投影、局部亮面 | 适合概念强调，与真实 UI 层明确区别 |

界面正文优先清晰的中文无衬线字。编辑标题可有不同字形，但一段内不要频繁换字体。图片保留内容和比例，避免只把图片当背景纹理。已有产品截图保持真实结构，别为统一风格强行改造成虚假的按钮和数据。

## 4. 布局自由，阅读路径明确

每段先选一个合适的主布局：左右对照、上下工作区、列表与详情、工具栏与画布、全屏局部操作、自由对象图等。可在动作中演变，不能每期固定“居中大标题＋三卡片”。

竖屏逻辑宽 544，高度可用约 967.111；源比例为 544×720。高度增加后重新排布，不纵向拉伸。字幕区与人物位置在设计时保留，尤其避开按钮、结果或正在强调的字段。人物是否全屏、画中画或隐藏由内容与已有素材决定；不默认新增数字人。

一段时间只设一个阅读重点，但不必清空其他内容。当前操作可由位置、大小、选中态、局部色彩和相机体现；上下文继续存在，有助于用户认出这是同一个空间。

## 5. 状态设计先于转场

为关键对象保留稳定 ID，写一张短表：

| 对象 | 初始状态 | 触发动作 | 结果状态 |
|---|---|---|---|
| 当前条目 | 普通、可识别的真实内容 | 用户选择 | 选中、详情区同步更新 |
| 结果区 | 等待输入或展示旧值 | 参数变化/任务完成 | 展示具体新内容并停留 |

表格是示例；本期可以完全采用其他对象和操作。不需要每段都包含光标，也不需要机械地完整走完“搜索→复制→粘贴→上传”。状态变化首先说明话意，转场负责连接阅读任务。

用实测口播关键词安排变化。控制抵达、点击、反馈之间保留可感知的先后；结果出现后留出阅读时间。次要层可有轻微跟随，但不要为了“动态”让所有元素同时抖动。

## 6. 组合实现

常规新界面使用 `mechanism: "ui-stage"` 与 `content.items: []`。`content.ui` 提供：

- `nodes`：带稳定 ID 的 `panel/text/button/input/badge/image/progress/line/chart/cursor`；自由指定 `x/y/w/h` 与内容。
- `tracks`：按 `nodeId` 写 `frames`，每帧使用场景局部时间 `at`、要改变的字段 `set` 和可选 `ease`。对象变的是状态，不是每句话重建一张场景卡。
- `camera`：用 `at/x/y/scale` 指定阅读焦点，先建立位置，再靠近关键内容，必要时回拉。
- `canvasHeight`：常用 9:16 为约 967.111，3:4 为 720，保持素材比例。
- `showTitle: false`：自行安排标题时关闭默认标题，用文字节点统一布局。

完整可用字段、范围、资源路径和时间要求以 [组合契约](ui-composition-contract.md) 为准。不要从本文缩略说明猜测额外字段。已有完整场景只是另一种复用方式，不限制 `ui-stage` 的布局和状态链；不足时按 [扩展约定](source-style-extension.md) 补部件。

## 7. 渲染前的五个具体判断

1. 截取一张中段画面，能否认出这期在讲什么，而不只是泛用科技卡片？
2. 隐去字幕，界面结构和动作是否仍表达了主要关系？字幕不必逐字对应图形，但不能承担全部解释。
3. 操作前后是否真的改变了可见内容、选择、参数或结果？
4. 以手机尺寸看，当前重点能否读清，同时知道它来自哪里？
5. 换一个主题时，能否重新组合布局和状态，而不被某个演示的剪辑顺序限制？

先渲染本期开头 10–15 秒并连续看听。用户对整体 UI 气质的实际反馈决定是否进入全片。技术校验用于发现字段或渲染问题，不能代替这种判断，也不证明较轻模型已通过当前机制的实际试用。
